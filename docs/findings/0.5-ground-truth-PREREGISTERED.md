# Phase 0.5 — ground truth, pre-registered

**Frozen 2026-08-28, BEFORE any proposal was generated.** This exists so the test cannot be graded against a target moved after seeing the answers. Committed first, deliberately.

**Data:** [`NH_HealthCitations_Aug2026.csv`](https://data.cms.gov/provider-data/dataset/r5ix-sfxw), CMS Provider Data Catalog, downloaded 2026-08-28. 165,336,194 bytes, **419,479 data rows**, 23 columns.

**Test file:** `sample_state.csv` — the first 400 Montana rows, contiguous, chosen to resemble what a regional office actually exports (repeat facilities, multiple surveys each) rather than a random national sample (which gave 298 distinct facilities in 300 rows and would not test entity resolution at all).

---

## Semantic anchor — CMS's own words, not my reading

> "A list of nursing home health citations in the last three years, including **the nursing home that received the citation**, **the associated inspection date**, citation tag number and description, scope and severity, the current status of the citation and the correction date. **Data are presented as one citation per row.**"

— dataset `description`, CMS metastore API

That sentence establishes the three-level structure independently of my judgement.

---

## The correct reading

**Three entity types, not one.** The file is flat; the structure is three-level.

| Entity | Key | Count in test file | Properties |
|---|---|---|---|
| **Nursing home (Facility)** | `CMS Certification Number (CCN)` | **10** | Provider Name, Provider Address, City/Town, State, ZIP Code |
| **Survey (Inspection)** | (CCN, Survey Date, Survey Type) | **69** | Survey Type, Inspection Cycle |
| **Citation (Deficiency)** | one per row | **400** | Deficiency Prefix, Category, Tag Number, Scope Severity Code, Deficiency Corrected, Correction Date, 5 Y/N flags |

**Relationships:** Citation → *issued during* → Survey → *conducted at* → Facility. (Citation → *received by* → Facility directly is also defensible; CMS's own sentence says the nursing home "received the citation".)

---

## The seven traps — every answer counted, not estimated

Method is stated per row. Full-file numbers come from `characterize.py` over all 419,479 rows; test-file numbers from the 400-row sample.

| # | The trap | Correct answer | How it was established |
|---|---|---|---|
| **T1** | `Deficiency Corrected` reads as a boolean from its name | **A status enum with SIX values, none of them yes/no**: `Deficient, Provider has date of correction` (408,475), `Past Non-Compliance` (6,115), `Deficient, Provider has plan of correction` (2,638), `Deficient, Provider has no plan of correction` (1,607), `Waiver has been granted` (367), `No revisit needed` (277). Four appear in the test file | counted, full file |
| **T2** | `Correction Date` is assumed to follow `Survey Date` | **It does not, in 5,338 of 416,948 rows = 1.28%.** In the test file, **6 of 400 = 1.5%**. Any "days to correct" or "overdue" metric is silently wrong for these rows | counted, full file + test file |
| **T3** | `Location` looks like new information | **99.988% redundant** — exactly rebuilt by joining Provider Address, City/Town, State, ZIP Code in 419,428 of 419,479 rows. **400 of 400 in the test file.** It is not a second entity and not a new property | counted, full file + test file |
| **T4** | `Provider Name` looks like the facility identifier | **CCN is the key.** CCN→name is perfectly 1:1 (0 CCNs carry more than one name), but **104 distinct names are shared by more than one CCN.** Resolving on name merges genuinely different facilities | counted, full file |
| **T5** | `Deficiency Description` looks like per-citation free text | **It is a lookup on `Deficiency Tag Number`.** 267 distinct tags across the full file, **0 with more than one description**; 92 tags in the test file, 0 with more than one. Description belongs to the tag, not the citation | counted, full file + test file |
| **T6** | A flat CSV reads as one entity type | **Three levels** (table above). Collapsing them makes per-facility and per-survey questions unanswerable without re-deriving the grain | derived from CMS description + key counts |
| **T7** | `Processing Date` looks like a meaningful date | **Single value for every row** (`2026-08-01`) — the export stamp. Zero information. Same for `Survey Type` *within this file* (only `Health`), which is an artefact of the slice, not of the dataset | counted, test file |

## Scoring rules, fixed in advance

A fresh agent, blind to this document, receives `sample_state.csv` and is asked to produce a reading of the file. It is **not** told what to look for, how many entities exist, or that traps exist.

**Score 1 — entity structure.** Did it find the three levels and the right keys? `correct` / `partial` / `wrong` per level.

**Score 2 — trap rate.** For each of T1–T7 independently: **avoided** (got it right, explicitly or implicitly), **fell in** (asserted the wrong thing), or **silent** (did not address it). **Silence counts as falling in for T1, T2 and T3**, because a proposal that quietly carries a wrong assumption into a metric is exactly the failure mode this product claims to prevent. Silence on T4–T7 is scored separately as "not addressed".

**Score 3 — correction rate.** The headline number. Count every distinct factual claim the proposal makes about structure, keys, column meaning, or data quality. Divide the claims a domain expert would have to correct by the total. **This is the number the venture's core usability bet rests on.**

**Score 4 — calibration.** Did it flag its own uncertainty where the data is genuinely ambiguous, or assert uniformly? Uncertainty that lands on real ambiguity is a *positive*; the walkthrough's step 2 depends on it.

## Pre-registered prediction

**[Assumed]** — recorded now so it cannot be revised after the fact: the entity structure (Score 1) will be largely correct, because the domain is legible and the CMS description is inferable from column names. **The traps are where it will fail**, particularly T2 (the temporal anomaly, which requires actually computing something rather than reading headers) and T5 (which requires noticing a functional dependency across rows).

**If T2 is missed by every agent, that is the single most important result in Phase 0** — it means the proposal engine produces confident, plausible, silently-wrong readings, and step 5 of the walkthrough (impact analysis) becomes load-bearing rather than a nice-to-have.
