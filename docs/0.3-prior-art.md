**Status:** Complete, 2026-08-28. Satisfies `ROADMAP.md` §0.3's exit criterion.

**Scope:** this asks one question only — *is any existing interface worth matching, for migration purposes?* It is not a survey and it is not a design input.

---

## The verdict, in one paragraph

**No existing interface is worth matching call-for-call, and one existing *vocabulary* is worth matching field-for-field.** [Observed] Both candidates are pure *declaration* registries: you hand them a finished type and they store it. `foundry-ontology-open`'s `Ontology` class exposes five `register_*` methods plus `get_linked_types`, `validate_ontology`, `summary` and `to_dict` — and has **no** proposal, approval, retirement, usage, provenance or consumer concept anywhere in it. Foundry's own public Ontology API is **read-only for type metadata**: there is a documented `GET .../objectTypes` and a `GET .../fullMetadata`, and an **open** feature request (palantir/foundry-platform-python#318, opened 2026-01-19) asking for endpoints to create object/link/action types at all, with the documented alternative being to author them in the Ontology Manager UI or in a SuperRepo. So the thing this project is actually building — the proposal→approval loop, with `consumers`, lifecycle and provenance — **has no prior art in either**, and matching their call shape would buy nothing while costing the loop. [Inferred] What *is* worth matching is Foundry's identifier-and-lifecycle vocabulary, because migration compatibility here means being able to *ingest a Foundry metadata dump*, not being called the same way: Foundry object types carry an ID / `apiName`, display name, plural display name, description, `primaryKey`, `properties {name → {baseType, description}}`, groups, `visibility ∈ {prominent, normal, hidden}` and — the one that matters — **`status ∈ {active, experimental, deprecated}`**. Our `status: proposed | active | retired` should be able to round-trip that. **The asymmetry is the practical finding:** a customer can be migrated *off* Foundry through the read API today, and cannot be migrated *onto* it through any public API today, so "match Foundry so we can hand data back" is not a real requirement — the door only opens one way.

## What this changes in Phase 1 — three items, and no more

1. **Do not copy the `register_*` shape.** [Observed] It is a declaration API. `propose_type` is not `register_object_type` with a different name, because the point is that the call may return a *proposal* rather than a stored type. Matching it would smuggle "the caller already decided" into the centre of a design whose thesis is that the caller has not decided.
2. **Match Foundry's status vocabulary well enough to round-trip.** [Observed] `active` / `experimental` / `deprecated` exists and is what a migrating customer's types are already tagged with. Phase 1's `status: proposed | active | retired` must state how it reads a Foundry `experimental` — candidate: `active` plus a predicate, **not** `proposed`, because `proposed` here means *not yet approved*, which `experimental` is not.
3. **Carry `apiName` / ID, `rid` and `primaryKey` through as opaque provenance, not as our own fields.** [Inferred] A migrated type needs to keep its Foundry identifiers so a later diff can say what came from where. That is the `provenance` slot's job, and it is cheap insurance on a one-way import.

**What this explicitly does not license:** copying object / link / action as *the* three kinds. `foundry-ontology-open` has them because Foundry has them; Foundry has them for its own historical reasons. Finding 0.1 says the kinds this registry needs are driven by capability predicates, and that question is settled by our own evidence, not by matching a shape.
