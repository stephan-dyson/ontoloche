# Rulings 2026-08-30 — the twelve questions row 4c left (Q49–Q60 → R48–R57, two flagged to the founder)

Supervisor rulings under the founder's make-assumptions directive. Source: [`docs/runs/4C-RUN.md`](../runs/4C-RUN.md) §8. Each is yes/no on the worker's recommendation; the founder may reverse any. **Two questions are product-level and are NOT ruled here — Q50 and Q56 — each carries a default that is in force until the founder speaks.** Three of the ten rulings create a new build row, **4d — identity staleness**, sequenced immediately, because it is the only row that closes the kill-row *class* the sixth trip named rather than another case of it.

## R48 (Q49) — `endpoint_type_merged` KEEPS its name. Recorded.
The value names a fact about the vocabulary (this reference's identity spans more than one written name), and R38 changed what the registry does with that fact, not the fact. Renaming a closed-vocabulary value for a change in consequence breaks R3's stability promise for nothing; §5.4 and EDGES §2.8 were amended in the same commit, which is what R3 asks.

## Q50 — may a `stores_proposals=False` backend hold a `kind="predicate"` entry at all? *FLAGGED TO THE FOUNDER — not ruled.*
**Default in force:** yes, written with warning `predicate_requires_review` (row 4c's behaviour, pinned `C10-10`), revisited with beacon 2B's evidence. The alternative — `Refusal(reason="proposals_not_stored")` — would mean beacon's own shape (PACKAGE §7.4) cannot carry a capability predicate, which decides what the registry declines to *serve*; that is the founder's. The kill row's danger is a predicate going live *and then being merged*, and the merge is guarded on every backend regardless of this answer.

## R49 (Q51) — `_IDENTITY_CHAIN_CAP = 16` stays a constant, NOT a `NamespacePolicy` field. Recorded.
A tunable bound on a pathological case (a cycle §5.9 does not forbid constructing) is configuration nobody sets correctly; R36 already ruled the assembly bound per-registry. Revisit only if a fixture ever shows a legitimate chain longer than 2.

## R50 (Q52) — the identity closure does NOT extend to `resolve_type`'s `alternatives` in v0. Recorded.
Scoring a near-miss against a merged-away word is a scoring question, not an identity question; R6's `search_namespaces` is the surface that would answer it. Recorded so the next scoring change reads this first.

## R51 (Q53) — `edge_payload` stays OUT of INTERFACE §2.2's kind vocabulary; PACKAGE §5.2 says so. DONE in row 4c.
An `AttributeSchema.kind` is a schema namespace, a `TypeEntry.kind` is a word in the vocabulary; conflating them is §2.3's Cause B (the exact defect D-4c-1 was). The PACKAGE §5.2 box was written by round 1 ([`PACKAGE.md`](../specs/PACKAGE.md), *"One kind's 'name' is not a type name"*), so nothing is owed.

## R52 (Q54) — `IDENTITY_FIELDS` stays DECLARED, not derived; the residual is stated in the file. Recorded.
Deriving it means knowing which `TypeRecord` fields `resolve_type` reads — a dataflow question a checker of this size should not answer. The residual (a third identity field added without touching the tuple is invisible) is stated in [`check_merge_guard.py`](../tools/check_merge_guard.py)'s header, and the sixth trip already exercised it: `status` was added as a narrowly-scanned third field with *its* gap (a computed key) stated too. The ruling is that gaps are written down, not that there are none.

## R53 (Q55) — the identity guards ARE worth extracting into one function — in the ACTIONS build row (6b), not before.
Five callers now carry copies (`merge_types`, `retire`, `import_types`, `reinstate`, `propose_type`). Extraction is a refactor with no new behaviour, and this row's evidence is that the checker — not a shared function — catches the next caller. Row 6b adds the sixth surface and is where the refactor pays for itself. **Row 4d must not do it** (see R54: 4d changes what the guards compare, and changing the guards' shape in the same row is how trips 2, 5 and 6 happened).

## Q56 — should an identity claim be verified where it is MADE (`resolve_type`'s 1.0), or only where it is WRITTEN? *FLAGGED TO THE FOUNDER — not ruled. This is the sixth trip's root cause and the only question that closes a class.*
**Default in force (row 4d):** the *cheap half* — when an exact hit is answered through an alias or successor, `resolve_type` re-reads both predicate extents and, if they no longer agree, still returns the redirect but carries a new warning (`identity_stale`, or the value the row mints under R3) instead of answering silently at 1.0. That is Rule U applied at the read, and it costs one extent read per alias hit on predicates only. **The expensive half — refusing to answer, or lowering the confidence below 1.0 — changes INTERFACE §5.3's shipped guarantee and decides what the registry declines to answer; that is the founder's.** Recorded with the sixth trip in [`2026-08-29-3c-rulings-R6-R12.md`](2026-08-29-3c-rulings-R6-R12.md).

## R54 (Q57) — `_extent` and `predicates()` resolve the IDENTITY, not the written word — in row 4d, under a staleness axis in the checker first.
After a merge, `list_types(predicate=survivor)` misses every type that declared the absorbed name and `predicates(of=…)` answers `known=0` — §5.2's own named failure mode. The fix is one line; the reason it was refused at round 3's cap is correct (`_extent` is the expression all six trips run through). So it lands **in its own row, after** `check_merge_guard.py` gains a **staleness** state — an extent pair that agreed at write time and differs at read time — so the change lands under a gate that can see it.

## R55 (Q58) — `propose_type` and `import_types` WARN when a declared predicate resolves to another identity. Row 4d, same change as R54.
Same fact reported at the write door; cheap; new warning value under R3 with its §5.4 row in the same commit.

## R56 (Q59) — `retract_edge`'s `status` write is NOT an identity write; the entry stays documented in `KNOWN_CALLERS`, not excluded. Recorded.
A scan that guesses which record shape a field belongs to is a scan with a judgement in it, and the judgement belongs where a reviewer can find and disprove it — which is exactly how the sixth trip found `reinstate`'s wrong verdict.

## R57 (Q60) — `direction` is NOT per-hop in v0; recorded against Phase 3's paging decision (R13/R25).
The flagship two-hop query (`task --blocks--> task --stakeholder--> person`) needs `in` then `out`; `direction="both"` reaches the right people and cannot say which is which. Both this and paging are about a read seam that cannot say enough about what it returned; they are one Phase 3 decision. Beacon slice 1 is told not to depend on per-hop direction (relay of 2026-08-30).
