## R38 (Q33) — `neighbors` FOLLOWS a merged type's successor chain: YES, row 4c. *Founder-visible.*
`resolve_type` already follows it (C3-11); one identity model per call is a defect, not a choice. **What changes:** an edge endpoint reference resolves to *the identity the reference now belongs to*, not *the reference that was written* — an INTERFACE §2.1 question, ruled here for both documents. **The honesty rule that comes with it (Rule K):** every edge reached through a successor hop carries a `via_successor` marker on the `NeighborEdge`, so a caller can tell a written reference from a followed one; `complete` stays about what was searched. **Why it matters to the founder:** this is what makes `merge_types` *safe on a store with edges in it* — after a merge, the graph still finds its way to the surviving type. Without it, a merge silently orphans every edge written against the merged-away name. 4c carries a contract id that proves it on all three legs and a broken-backend test that stops following at depth.
